# 出行助手设计说明

## 背景

当前项目是一个基于 Next.js App Router 的桌面优先后台应用，现有导航与页面均围绕记账功能组织。新增“出行助手”时，需要同时解决两个问题：

1. 将现有导航从“平铺的记账菜单”升级为“一级业务分组 + 二级功能菜单”。
2. 新增一个基于高德地图的桌面端路径规划工作台，支持搜索和地图点选两种入口。

## 目标

- 在侧边栏中引入两个一级分组：`记账` 和 `出行`
- 将现有 `概览 / 账单记录 / 统计分析 / 设置` 收拢到 `记账` 二级菜单下
- 在 `出行` 一级分组下新增 `出行助手` 二级菜单，路径为 `/dashboard/travel`
- 在出行助手页面实现桌面端双栏布局
- 左侧支持起点、终点搜索、候选结果列表、出行方式切换和手动触发路径规划
- 右侧支持高德地图展示、地图点击选点、详情卡片展示和路径渲染

## 非目标

- 本期不做移动端专项体验设计，仅保证桌面布局不会在移动端直接报错
- 本期不支持公交路线，只支持 `驾车 / 步行 / 骑行`
- 本期不做收藏地点、历史路线、路线比较、多点途经等扩展能力
- 本期不引入新的后端持久化数据结构

## 用户场景

### 场景 1：通过搜索完成路径规划

1. 用户进入出行助手页面
2. 页面自动尝试定位当前位置，并填充到起点输入框
3. 用户聚焦起点或终点输入框并输入关键词
4. 左侧候选结果列表跟随当前激活输入框展示搜索结果
5. 用户从结果列表中选中地点
6. 用户选择出行方式后点击“确定”
7. 地图绘制规划结果，并展示路线摘要

### 场景 2：通过地图点选终点完成路径规划

1. 用户进入页面并完成或跳过自动定位
2. 用户在地图上点击某个位置
3. 页面对点击坐标执行逆地理编码和周边地点解析
4. 地图侧展示详情卡片，包含名称、地址、图片
5. 用户点击“去这里”
6. 该地点作为终点写入当前状态，并立即开始路径规划

页面采用桌面端双栏工作台：

- 左侧固定控制台

## 交互设计

### 起点逻辑

- 页面加载时自动尝试定位当前位置
- 定位成功后将结果写入起点状态，并允许用户继续手动修改
- 定位失败时不阻塞页面，提示用户手动输入当前位置

### 搜索与候选列表

- 左侧候选结果列表与当前激活输入框绑定
- 当前聚焦起点输入框时，列表展示起点候选
- 当前聚焦终点输入框时，列表展示终点候选
- 点击候选项后，将所选地点写入对应输入框状态
- 如果输入内容变化，应清空与之失配的已选地点对象，避免文字与实际坐标不一致

### 出行方式

- 支持 `驾车 / 步行 / 骑行`
- 默认选中 `驾车`
- 在存在有效起点和终点时切换出行方式，应触发重新规划
- 在尚未满足规划条件时切换，仅更新方式状态，不自动发起请求

### 手动规划

- 当且仅当起点与终点都存在有效坐标时，“确定”按钮可用
- 点击“确定”后进入规划中状态
- 规划中需禁用重复点击

### 地图点选

- 用户点击地图后，使用逆地理编码解析点位
- 页面展示详情卡片，优先显示：
  - 名称
  - 地址
  - 图片
- 点击“去这里”后，将该地点设为终点并立即开始规划

### 路线结果

- 成功规划后在地图上绘制路线
- 页面展示路线摘要，至少包括：
  - 当前出行方式
  - 预计距离
  - 预计时长
- 后续若用户修改起点、终点或方式，应使当前路线结果失效并重新进入待规划状态，或直接触发重规划

## 状态模型

页面核心状态建议如下：

- `originInput`: 起点输入框文本
- `destinationInput`: 终点输入框文本
- `originPlace`: 当前起点地点对象
- `destinationPlace`: 当前终点地点对象
- `activeField`: 当前激活输入框，值为 `origin` 或 `destination`
- `searchResults`: 当前候选结果列表
- `travelMode`: 当前出行方式，值为 `driving`、`walking`、`riding`
- `selectedMapPlace`: 地图点选后的详情对象
- `routeResult`: 当前路线结果
- `isLocating`: 是否正在定位
- `isSearching`: 是否正在搜索
- `isPlanning`: 是否正在规划
- `pageError`: 页面级错误提示

推荐状态阶段：

1. `定位中`
2. `编辑起点或终点`
3. `已选目的地，待规划`
4. `规划中`
5. `已生成路线`

## 组件边界

### 页面容器

负责整页状态编排与高层数据流，不直接承载复杂地图调用细节。

职责：

- 管理起点、终点、出行方式、候选结果、规划状态
- 编排左侧面板与右侧地图面板之间的数据流
- 接收地图点选结果并决定是否立即规划

### 左侧搜索面板

职责：

- 渲染输入框、结果列表、出行方式和确定按钮
- 派发搜索行为
- 根据当前焦点绑定结果列表含义

约束：

- 不直接持有地图实例
- 不直接执行地图绘制

### 右侧地图面板

职责：

- 初始化与销毁高德地图实例
- 响应地图点击事件
- 展示详情卡片
- 绘制路线与地图覆盖物

约束：

- 不负责管理左侧候选列表逻辑
- 不直接控制输入框文本

### 高德服务适配层

建议将高德能力封装为独立的客户端工具层，至少覆盖：

- 地图加载与插件初始化
- 定位
- 输入提示或地点搜索
- 逆地理编码
- 驾车路径规划
- 步行路径规划
- 骑行路径规划

这样可以把具体 JSAPI 调用和 React 组件隔离，降低页面组件复杂度。

## 数据流

### 搜索路线流

1. 用户聚焦输入框并输入关键词
2. 页面根据 `activeField` 发起地点搜索
3. 搜索结果进入 `searchResults`
4. 用户点击结果项
5. 页面更新对应地点对象与输入框文本
6. 用户点击“确定”
7. 页面根据 `travelMode` 调用对应路线规划服务
8. 成功后更新 `routeResult` 并通知地图绘制

### 地图点选流

1. 用户点击地图
2. 地图面板返回坐标
3. 页面调用逆地理编码与地点详情解析
4. 页面更新 `selectedMapPlace`
5. 详情卡片展示名称、地址、图片
6. 用户点击“去这里”
7. 页面将 `selectedMapPlace` 写入终点状态
8. 若起点有效，则立即开始规划

## 异常处理

### 定位失败

- 不阻断页面初始化
- 显示轻量提示
- 引导用户手动搜索起点

### 搜索无结果

- 候选结果列表展示空态
- 不弹阻断式错误

### 地图点选详情不完整

- 名称、地址、图片按可用字段降级展示
- 图片缺失时使用占位内容
- 仍允许用户点击“去这里”

### 路径规划失败

- 保留当前起点、终点与方式
- 展示明确错误提示
- 允许用户直接重试或改点位

### 重复请求

- 搜索与规划阶段分别加 loading 状态
- 规划中禁用“确定”和“去这里”

## 技术约束

- 采用高德地图 JSAPI v2.0
- 高德鉴权需要在地图加载前正确配置 `window._AMapSecurityConfig`
- 地图组件卸载时必须显式销毁地图实例，避免内存泄漏
- 生产代码只按需加载所需插件
- 页面以桌面优先为准，不额外承担移动端复杂自适配

## 测试范围

### 组件与状态测试

- 侧栏分组与新入口渲染正确
- 激活起点框时，结果列表服务起点
- 激活终点框时，结果列表服务终点
- 未满足起终点条件时，“确定”按钮不可用
- 地图点选后能展示详情卡片
- 点击“去这里”后能将地图点选目标写入终点状态
- 切换出行方式时，状态与规划行为符合预期

### 交互回归测试

- 自动定位成功时能填充起点
- 自动定位失败时页面仍可操作
- 搜索无结果时显示空态
- 路径规划失败时不丢失已选状态

## 风险与注意事项

- 当前项目尚未集成高德 JSAPI 相关依赖和密钥配置，首次接入时需补足环境变量与安全配置
- 当前会话生成了 `.superpowers/` 临时可视化文件，后续如继续使用该工作流，建议将其加入 `.gitignore`
- 路线规划与地点详情均依赖高德返回结构，适配层需要做字段收敛，避免直接把原始返回对象散落到组件中

## 实现建议

按以下顺序推进实现最稳妥：

1. 重构侧栏导航结构，引入一级分组与二级菜单

3. 抽出高德加载与服务适配层
4. 先实现搜索选点与地图点选的状态流
5. 再接入驾车、步行、骑行三种路线规划
6. 最后补异常态和测试
